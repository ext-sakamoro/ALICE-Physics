# Gate oracles — checking that the checks can fail

A gate is anything that can turn the build red: a workflow job or step, a
script under `scripts/` (ratchet, lint, guard, status generator), or a step of
`scripts/preflight.sh`. A gate that cannot fail is worse than no gate: it
reports green for code nobody checked. An audit of every gate (origin/main
`14fd52a8`) found several that pass while comparing nothing — a semver check
whose failure is discarded, fuzz targets that are never built, tests that a
`cfg` removes from every lane, ratchets that accept a run that tested one
mutant out of hundreds.

This document specifies how a gate is itself tested, so that such a gate is
found by the build and not by a later audit.

## 1. Terms

| Term | Meaning |
|---|---|
| **gate** | one command whose exit status decides red or green |
| **must-red control** | an input on which the gate has to fail: an empty input, two empty sides of a comparison, a malformed input, a target removed by `cfg`, a cancelled or timed-out run, a known defect |
| **must-green control** | an input on which the gate has to pass: a small, correct case of what it checks |
| **gate oracle** | the pair of controls for one gate, plus the expected exit status and the line of output that names the reason |
| **canary** | a commit carrying a known defect, pushed to an isolated `ci/canary-*` branch, to see a workflow job turn red on the real runners |

A must-green control alone proves nothing (an `exit 0` passes it). A
must-red control alone does not prove the gate can pass. Both are required.

## 2. Layout

```
scripts/gate_oracles/
  gates.toml              # one entry per gate (section 3)
  <gate-id>/
    red-<case>/           # files the gate reads, laid out as in the repository
    green-<case>/
scripts/gate_oracle_check.py   # the runner (section 4)
docs/gate-oracle-status.md     # generated ledger (section 5)
```

A control is a directory holding only the files the gate reads (a summary
file, a `mutants.out` tree, a `Cargo.toml` and one test file, a workflow
file). The runner copies it into a fresh temporary directory and runs the gate
there, so a control can never read or change the working tree.

## 3. `gates.toml`

```toml
[[gate]]
id = "mutants-ratchet"
kind = "script"                       # script | workflow-step | preflight-step
source = "scripts/mutants_ratchet.py" # where the gate is defined
run = "python3 {script} --out {dir}/mutants-out-default --baseline {dir}/baseline.txt"
cost = "fast"                         # fast (< 10 s) | cargo (needs a build)

[[gate.control]]
case = "red-one-of-many-tested"
expect = "fail"                       # fail | pass
reason = "tested 1 of"                # a substring the output must contain
```

`{script}` is `source`, `{dir}` the temporary copy of the control. A gate
whose decision depends on a workflow expression (for example a `|| true`, a
`continue-on-error`, or a `matrix` list) is declared with
`kind = "workflow-step"` and checked by the static rules of section 6 in
addition to, or instead of, controls.

## 4. Runner `scripts/gate_oracle_check.py`

For every gate and every control:

1. copy the control to a temporary directory;
2. run `run` with a time limit (60 s for `fast`, 15 min for `cargo`);
3. compare the exit status with `expect`, and require `reason` in the output
   (stdout and stderr together), so that a gate failing for an unrelated
   reason — a missing file, a traceback — does not count as the expected red.

The runner fails when:

- any control has the wrong exit status or lacks its `reason`;
- a gate has no must-red control or no must-green control;
- `gates.toml` names a `source` that does not exist;
- it ran no control at all (the runner's own empty-input case).

The runner is a gate too, and has its own controls: a stub gate that always
exits 0 must be reported as failing its must-red control, and a stub that
always exits 1 as failing its must-green control. These two stubs live in
`scripts/gate_oracles/runner/` and run first.

`cost = "fast"` controls run in `ci.yml` on every push (one ubuntu job,
budget under 2 minutes) and in `preflight.sh --quick`. `cost = "cargo"`
controls (a test file whose only test is removed by `cfg`, a feature lane
that runs zero tests) run in the full preflight and in the weekly workflow,
not on every push, so that the per-push job stays within its budget.

## 5. Ledger `docs/gate-oracle-status.md`

Generated by `scripts/gen-gate-oracle-status.py`, checked with `--check` in
`ci.yml` the same way as `docs/oracle-status.md`.

The generator enumerates gates from the sources, not from `gates.toml`:

- every `run:` step of `.github/workflows/*.yml` that calls `cargo test`,
  `cargo mutants`, `cargo fuzz`, `cargo miri`, `cargo semver-checks`, or a
  script under `scripts/`;
- every script under `scripts/` that is called from a workflow or from
  `preflight.sh` and exits with a status;
- every `step` of `preflight.sh`.

Each enumerated gate is matched to a `gates.toml` entry by `source` (and, for
workflow steps, by workflow file and step name). The ledger lists every gate
with its controls and their last result. The check fails when:

- an enumerated gate has no entry (a new gate was added without controls);
- an entry matches no enumerated gate (a stale entry);
- the number of enumerated gates is zero.

This is the gate counterpart of `scripts/wiring_guard.py`: adding a gate
obliges adding its controls in the same change.

## 6. Static rules for workflow-defined decisions

Some gates decide in YAML rather than in a script. The generator also checks:

| Rule | Fails when |
|---|---|
| no discarded failure | a gate step ends in `\|\| true`, or has `continue-on-error: true`, unless the step is listed as `informational` in `gates.toml` (and then it cannot be counted as a gate) |
| matrix matches its source | a fuzz matrix differs from the `[[bin]]` list of `fuzz/Cargo.toml`; a feature-gated test lane list differs from the features that `#[cfg(feature = …)]` uses in `tests/` |
| every `cfg` reaches a test lane | a `#[cfg(feature = "X")]` (or `target_arch`, `not(debug_assertions)`, `not(feature = "std")`) in `tests/` or `src/` test modules has no lane that both enables it and runs `cargo test` without `--lib` (or, for `src/`, with `--lib`) |
| cancellation is not success | a scheduled job whose `timeout-minutes` was reached in the last completed run, or whose last run ended `cancelled`, is listed as *unverified* in the ledger |

The last rule reads the conclusions of the latest scheduled runs through the
GitHub API in the weekly workflow only; a job that has not completed since its
definition last changed is shown as *unverified*, not as green.

## 7. Canaries on the real runners

Controls run a gate on chosen inputs; they do not show that the workflow
around it runs the gate at all (a wrong `paths` filter, a job never
scheduled, a matrix that skips the case). For that, a canary:

1. a branch `ci/canary-<gate-id>` from the current `main`, holding one commit
   that introduces a known defect the gate exists to catch (section 8 gives
   the defect for each gate);
2. pushed when the gate's workflow file or script changes, and otherwise at
   most once a month per gate;
3. the expected job must end `failure` with the documented reason in its
   log; `success` or `cancelled` is a failed canary;
4. the branch is deleted after the result is recorded in the ledger.

Runner use: check the queue before pushing (no queued or in-progress run of
the same workflow on `main`); push canaries one at a time; heavy workflows
(mutants, Miri, coverage) are not canaried on `ci/**` at all, since they do
not trigger there by design — their canary is the must-red control of their
ratchet plus the *unverified* rule of section 6. Expected cost per canary:
one ordinary CI run of the affected workflow (about 10–15 runner minutes for
`ci.yml`, about 1 minute for `fuzz.yml` with one target).

## 8. Controls for the gates found failing open

The eight highest-severity findings of the audit, each with the control that
would have caught it. "red" means the control must make the gate fail.

| # | Gate | Finding | Must-red control | Must-green control | Kind |
|---|---|---|---|---|---|
| 1 | nightly in-diff mutants (`quality-deep.yml`) | every run reached the 300-minute limit and ended `cancelled`; missed mutants found before the cut did not fail the run | static: a job reaching `timeout-minutes` or ending `cancelled` is *unverified*; control for the decision script: a `mutants.out` with `missed.txt` holding one line and the run marked timed out → fail with "missed" | a `mutants.out` with only `caught.txt` and a completed run → pass | workflow-step + script |
| 2 | `scripts/run_ignored.py` (weekly) | a `runtime:` test whose binary aborts, zero binaries, or an empty table all exit 0 | (a) a table row whose binary exits 134 without a result line → fail "did not run"; (b) zero binaries → fail "compared nothing"; (c) empty table → fail "compared nothing" | one row, one binary printing its `ok` line → pass | script |
| 3 | `cargo semver-checks` (`security-audit.yml`) | failure discarded by `\|\| true`; the rustdoc build fails on the mutually exclusive `wasm`/`ffi` features, so nothing is compared | static: `\|\| true` on a gate step → fail; control: a two-commit fixture crate whose second commit removes a `pub fn` → fail "removed" | the same crate with an added `pub fn` → pass | workflow-step |
| 4 | `fuzz.yml` matrix | 5 of 9 `[[bin]]` targets never built or run | static: matrix ≠ `[[bin]]` list → fail; control: a `fuzz/Cargo.toml` with a tenth `[[bin]]` not in the matrix → fail "not in matrix" | lists equal → pass | workflow-step |
| 5 | `simd`-gated integration tests | the only `simd` lanes run `--lib`; `tests/analytic_math_wiring.rs` `mod x86_64_simd_gated` runs nowhere | static rule "every `cfg` reaches a test lane": a `tests/` file with a `#[cfg(feature = "simd")]` test and no lane running `cargo test --features simd` without `--lib` → fail | the same file with such a lane → pass | workflow-step (static) |
| 6 | no_std test build | `cargo test --lib --no-default-features --no-run` does not compile (68 errors) and no lane runs it | static rule: `cfg(not(feature = "std"))` in `src/` with no lane running `cargo test --lib --no-default-features` → fail; canary: the lane added and a `vec!` used without import in a test module → the lane fails | the lane present and compiling → pass | workflow-step (static) + canary |
| 7 | `preflight.sh` full | no `cargo test --features parallel`, so `cfg(feature = "parallel")` integration tests run in CI but never locally | static: a CI `cargo test` argument set (features, `--lib`/not, target) missing from the full preflight → fail "not reproduced" | every CI test argument set present → pass | preflight-step (static) |
| 8 | `preflight.sh --fast` (`scripts/affected_tests.py`) | a selected target that runs 0 tests is hidden by the always-selected golden tests in the total | control: a selection of two targets, one of which is `#![cfg(not(feature = "parallel"))]` while the run enables `parallel` → fail "ran 0 tests" naming that target | both targets run ≥ 1 test → pass | script (`cost = "cargo"`) |

The medium findings (ratchets that accept one compared file or one tested
mutant, `gen-wiring-status.py` writing "All clear" when the guard did not
scan, `ci_load_check.py` matching only the literal `ci/**`, the re-export
check comparing 0 with 80, the bench check reading only one column, the JS
binding check counting tests instead of passes, the feature-gated test runner
counting per target instead of per gated module, the `ffi::`/`wasm::` filters
matching nothing) follow the same pattern: each gets a must-red control built
from the input that the audit fed it, and the fix is the lower bound that
makes that control fail.

## 9. Order of work

1. The runner, its two stub controls, and `gates.toml` for the scripts that
   already have unit tests (their empty-input tests become controls).
2. Controls and lower bounds for findings 2 and 8, then the medium script
   findings, one gate per change, each change adding the control first (red
   on the current gate) and then the bound (green).
3. The ledger generator and its `--check` in `ci.yml`.
4. The static rules of section 6 (findings 3–7).
5. Canaries for `ci.yml`, `fuzz.yml` and `downstream.yml`.

A gate is counted as checked in the ledger only after its must-red control
has been seen failing against the gate as it was before the fix.
